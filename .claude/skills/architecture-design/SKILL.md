# 아키텍처 설계 (SWE.2)

승인된 SW 요구사항(`docs/swe1/`)을 **컴포넌트와 인터페이스**로 구조화해 `docs/swe2/`에 쓴다. 이 산출물은 상세 설계의 틀이며, 통합 테스트(SWE.5)의 기준이 된다.

## 핵심 규칙

1. **모든 컴포넌트는 인터페이스를 가진다.** 인터페이스 없는 컴포넌트는 정의하지 않는다(외부와 주고받는 것이 없다면 컴포넌트가 아니다).
2. **컴포넌트끼리는 오직 인터페이스를 통해서만 통신한다.** 다른 컴포넌트의 내부 함수·전역 변수·내부 헤더에 접근하지 않는다.
3. **높은 응집도, 낮은 결합도.**
4. **모듈화, 캡슐화, SOLID**를 지킨다.
5. 모든 컴포넌트·인터페이스는 요구사항과 **양방향 추적성**을 가진다.

## C에서 규칙을 구현하는 방법

| 개념 | C 구현 | 검사 |
|---|---|---|
| 컴포넌트 | `src/<컴포넌트>/` 디렉터리 하나 | |
| 인터페이스 | 컴포넌트 공개 헤더 `<이름>_if.h` (함수 선언, 데이터 타입, 단위·범위·호출 주기는 Doxygen) | |
| 비공개 구현 | 같은 디렉터리의 `.c`와 `_if.h`가 아닌 헤더. 내부 함수는 `static` | `check_interfaces.py` I1, I2 |
| 캡슐화 | 상태 변수는 `.c`의 `static`. 헤더에서 `extern` 변수를 공개하지 않는다. 필요하면 getter/setter 함수를 인터페이스에 둔다 | I3 |
| 의존 역전 | 하위 컴포넌트(HW, 시간, 통신)는 인터페이스를 **함수 포인터 구조체**(ops)로 정의하고, 상위 컴포넌트는 그것을 인자로 받는다 | |
| 공유 타입 | 여러 컴포넌트가 쓰는 타입은 `src/common/`(예: `common/types_if.h`)에 두고, 아키텍처 문서에 "공유 디렉터리"로 명시한다. 공유는 타입·상수에 한정하고 로직을 넣지 않는다 | `--shared common` |
| 순환 의존 금지 | 의존 방향은 비순환 그래프여야 한다 | I4 |

## 설계 원칙 적용

### 응집도·결합도

- **응집도**: 컴포넌트는 한 가지 이유로 변한다. 컴포넌트 이름이 "and", "manager", "util", "common"이면 책임이 섞인 신호다. 책임을 한 문장으로 못 쓰면 쪼갠다.
- **결합도**: 인터페이스의 매개변수·반환 타입이 구현 세부(내부 구조체, 배열 크기)를 드러내지 않게 한다. 인터페이스가 넓을수록(함수 7개 이상, 매개변수 5개 이상) 결합이 높다. 좁은 인터페이스 여러 개로 나눈다.
- 컴포넌트 의존은 **데이터를 넘기는 방식**(값, 읽기 전용 구조체)으로 하고, 제어를 넘기는 방식(플래그로 동작 변경)을 피한다.

### SOLID (C 해석)

| 원칙 | 이 프로젝트에서 |
|---|---|
| S 단일 책임 | 컴포넌트·모듈은 변경 이유가 하나. 책임 문장에 "그리고"가 있으면 분리 |
| O 개방-폐쇄 | 새 동작(규칙, 신호원 추가)은 기존 컴포넌트 수정이 아니라 ops 테이블에 항목을 **추가**해서 확장 |
| L 리스코프 치환 | 같은 인터페이스(ops)를 구현한 대체물(실제 HW/스텁/시뮬레이터)은 인터페이스에 적은 전제·사후 조건을 똑같이 지킨다 |
| I 인터페이스 분리 | 사용자가 쓰지 않는 함수를 의존하게 만들지 않는다. 읽기용 인터페이스와 쓰기용 인터페이스를 나눈다 |
| D 의존 역전 | 상위 정책(판단 로직)이 하위 세부(HW, OS)를 직접 부르지 않고 인터페이스(ops)에 의존한다. 이것이 통합 테스트에서 HW·OS 경계를 스텁으로 바꾸는 지점이다 |

### 모듈화와 캡슐화

- 컴포넌트 하나는 독립적으로 빌드·테스트할 수 있어야 한다. 다른 컴포넌트가 필요하면 그 인터페이스만 보고 스텁으로 대체할 수 있어야 한다.
- 변경될 가능성이 큰 결정(임계값, 타이밍, 신호 매핑)은 한 컴포넌트에 가둔다.

## 절차

1. **입력 확인**: `docs/swe1/`의 요구사항·안전 요구사항. 요구사항 분석이 리뷰를 통과하지 않았으면 시작하지 않는다.
2. **컴포넌트 도출**: 요구사항을 책임별로 묶는다. 후보마다 책임 한 문장, 소유하는 데이터(상태), 변경 이유를 적는다. 안전 요구사항(SAF)을 구현하는 컴포넌트와 그렇지 않은 컴포넌트를 분리해 간섭을 막는다(ASIL/QM 분리).
3. **인터페이스 정의**: 컴포넌트마다 제공(provided)·요구(required) 인터페이스를 `references/templates.md` 양식으로 정의한다. 함수 시그니처, 매개변수의 단위·범위, 반환값(상태 코드 포함), 호출 주기·순서·재진입, 오류 처리를 쓴다.
4. **의존 그래프**: 컴포넌트 간 호출 관계를 그리고(마크다운 표 + mermaid) 순환이 없는지 확인한다. HW·OS 경계를 식별해 "스텁 지점"으로 표시한다.
5. **동적 동작**: 실행 순서, 주기, 상태 전이, 오류 전파를 시퀀스·상태 표로 쓴다(통합 테스트의 근거).
6. **자체 점검**: 아래 "점검 질문"을 모두 통과시킨다.
7. **추적성 검증**: 
   ```bash
   python3 .claude/skills/requirements-analysis/scripts/trace_check.py --docs docs --stage swe2
   ```
   모든 요구사항이 컴포넌트·인터페이스에 연결되고(T1), 모든 컴포넌트·인터페이스가 요구사항을 가져야(T2) 한다.
8. **리뷰**: `aspice-stage-review` 스킬로 `stage-reviewer` 서브에이전트에 리뷰를 맡긴다. 통과 전에는 SWE.3로 넘어가지 않는다.

## 점검 질문

- 모든 컴포넌트에 인터페이스가 정의되어 있는가? 인터페이스 없이 다른 컴포넌트가 부르는 함수가 있는가?
- 컴포넌트 책임을 한 문장으로 쓸 수 있는가?
- 의존 그래프에 순환이 있는가? 상위 컴포넌트가 하위 세부를 직접 부르는가?
- 어떤 컴포넌트를 스텁으로 바꿔도 나머지가 빌드·테스트되는가?
- 상태(전역)를 소유하는 컴포넌트가 하나로 정해져 있는가?
- 인터페이스마다 통합 테스트로 검증할 수 있는 합격 조건이 있는가?

## 코드와의 일관성

설계서의 컴포넌트·인터페이스는 구현 후에도 맞아야 한다. 구현 단계에서 규칙을 어기면 다음 검사가 실패한다.

```bash
python3 .claude/skills/architecture-design/scripts/check_interfaces.py --src src --shared common
```

(`tools/run.sh rules`가 이 검사를 포함한다.) 검사가 실패하면 코드를 고치거나, 설계가 틀렸다면 **설계서부터** 고치고 리뷰를 다시 받는다. 검사 규칙을 완화하지 않는다. `--shared`에 디렉터리를 추가하는 것은 아키텍처 문서에 공유 디렉터리로 명시한 경우에만 한다.

## 보고

호출한 쪽에 컴포넌트 수, 인터페이스 수, 의존 그래프 요약, 식별한 HW·OS 스텁 지점, 추적성 검사 결과(출력 그대로), 질의·가정, 리뷰 기록 경로를 돌려준다.
