# 상세 설계 (SWE.3 설계)

승인된 아키텍처(`docs/swe2/`)의 컴포넌트를 **모듈과 함수**로 분해해 `docs/swe3/`에 쓴다. 이 산출물에서 구현이 그대로 나오고, 단위 테스트(SWE.4)의 예상값이 도출되므로 **코드를 보지 않고도 함수 동작을 알 수 있을 만큼** 구체적이어야 한다.

## 핵심 규칙

1. **모듈을 정의한다.** 컴포넌트를 책임 단위의 모듈로 나눈다.
2. **일정 수준 이상의 모듈은 인터페이스를 반드시 정의한다.** 기준은 아래 표(프로젝트 기준).
3. **인터페이스가 정의된 모듈은 오직 인터페이스를 통해서만 통신한다.**
4. **클린 코드 원칙**을 설계 단계에서부터 지킨다.
5. **단일 책임 원칙**: 모듈도 함수도 변경 이유가 하나다.
6. 모든 모듈·함수는 아키텍처(CMP/IF)와 **양방향 추적성**을 가진다.

## 인터페이스가 필요한 모듈 — 수준 기준

아래 중 **하나라도** 해당하면 그 모듈은 인터페이스(`<모듈>_if.h`)를 반드시 정의한다.

| # | 기준 |
|---|---|
| M1 | 같은 컴포넌트의 다른 모듈 또는 다른 컴포넌트에서 호출된다 |
| M2 | 공개 함수가 3개 이상이다 |
| M3 | 안전 요구사항(SAF)을 구현한다 |
| M4 | 상태(static 데이터)를 소유한다 |

기준에 해당하지 않는 모듈(다른 곳에서 부르지 않는 내부 보조 모듈, 공개 함수 2개 이하의 순수 계산)은 인터페이스를 생략할 수 있고, 같은 컴포넌트 안에서는 직접 접근이 허용된다. 이 기준은 설계서 머리에 적고, 프로젝트가 바꾸려면 사용자 승인을 받아 이 표와 CLAUDE.md를 함께 고친다. 모든 모듈에 인터페이스를 만드는 것은 허용되지만 필수는 아니다.

C에서의 구현:

| 개념 | 구현 |
|---|---|
| 인터페이스가 있는 모듈 | `src/<컴포넌트>/<모듈>/` 디렉터리 + `<모듈>_if.h`(공개) + 비공개 헤더·`.c` |
| 인터페이스가 없는 모듈 | 컴포넌트 디렉터리 안의 `.c`/`.h` 쌍. 외부로 안 보이는 함수는 `static` |
| 모듈 간 통신 | 다른 모듈은 `<모듈>_if.h`만 include (`check_interfaces.py`가 검사) |

## 클린 코드 원칙 — 설계에 적용

| 원칙 | 설계서에서 지키는 방법 |
|---|---|
| 의미 있는 이름 | 이름은 의도를 드러낸다(`is_lock_condition_met`). 약어·`data`·`tmp`·`flag`·`do_it` 금지. 이름이 길어도 된다 |
| 작은 함수 | 함수는 한 화면(순수 코드 약 30줄)에 들어간다. 한 함수는 **한 가지 일**만 한다. 이름에 "and"가 필요하면 쪼갠다 |
| 추상화 수준 통일 | 한 함수 안에서 같은 수준의 일만 한다(고수준 흐름 함수가 비트 연산을 하지 않는다) |
| 매개변수 최소화 | 0~3개가 목표, 4개 이상이면 구조체로 묶거나 책임을 다시 나눈다. 출력 매개변수는 가급적 하나 |
| 부작용 없음 | 이름에 드러나지 않은 전역 변경을 하지 않는다. 상태를 바꾸는 함수는 이름과 설계서에 명시한다 |
| 중복 제거(DRY) | 같은 판정·변환이 두 곳에 나오면 함수 하나로 모은다 |
| 불리언 인자 금지 | 플래그로 동작을 바꾸는 함수는 둘로 나눈다 |
| 오류 처리 | 모든 함수가 상태 코드를 반환한다(아래 구현 규칙). 반환값을 무시하는 호출을 설계하지 않는다 |
| 주석은 이유를 | 코드가 말하는 "무엇"을 주석으로 반복하지 않는다. 설계서에 "왜"를 쓴다 |
| 매직 넘버 금지 | 임계값·크기는 이름 있는 상수로 정의하고 요구사항 ID와 연결한다 |

## 단일 책임 원칙(SRP)

- **모듈**: 책임을 한 문장으로 쓴다. "그리고", "및"이 들어가면 분리한다. 변경 이유가 둘이면(예: 임계값 정책과 신호 필터링) 모듈을 나눈다.
- **함수**: 같은 질문을 한다. 입력 검증 → 판단 → 출력 설정이 한 함수에 섞여 있으면 단계별 함수로 나눈다.
- 순환 복잡도 10 초과와 결정(decision)당 조건 7개 이상, 함수 라인수 80 초과는 SRP 위반의 신호로 보고 설계 단계에서 분할한다.

## 판단 로직은 결정표로

조건이 둘 이상인 판단은 **결정표**로 쓴다. 단위 테스트에서 MC/DC 벡터와 예상값을 여기서 도출한다(코드를 실행한 값으로 예상값을 정하지 않기 위해서다).

| 조건 | C1 `speed >= 15` | C2 `door_closed` | C3 `!manual_override` | 결과 |
|---|---|---|---|---|
| R1 | T | T | T | LOCK |
| R2 | F | - | - | NONE |
| R3 | T | F | - | NONE |
| R4 | T | T | F | NONE |

조건은 결정당 6개 이하를 권장한다. 조건이 N개면 MC/DC 테스트 벡터가 최소 N+1개 필요하고 이해·검증이 어려워지기 때문이다(LLVM 23은 7개 이상도 측정하므로 측정 한계는 아니다). 넘으면 중간 판정 함수로 나누거나, 나누지 않는 근거를 설계서에 쓴다.

## 절차

1. **입력 확인**: 승인된 `docs/swe2/` 아키텍처. 리뷰를 통과하지 않았으면 시작하지 않는다.
2. **모듈 분해**: 컴포넌트마다 모듈을 나누고 모듈별 책임 한 문장, 소유 데이터, 인터페이스 필요 여부(M1~M4 판정 근거 포함)를 적는다.
3. **모듈 인터페이스 정의**: 필요한 모듈마다 `MIF-nnn`으로 함수·타입·전제 조건을 정의한다. 컴포넌트 인터페이스(IF)를 구현하는 모듈은 해당 IF와 연결한다.
4. **함수 설계**: 공개 함수와 비공개 함수를 모두 `FN-nnn`으로 정의한다. 함수마다 목적(한 문장), 매개변수(단위·범위), 반환값(상태 코드 목록), 전제·사후 조건, 오류 처리, 알고리즘(결정표·상태표·의사 코드)을 쓴다. 양식은 `references/templates.md`.
5. **정적 구조 검토**: 의존 그래프를 그리고 순환이 없는지 확인한다. 모듈의 인터페이스 경유 규칙을 점검한다.
6. **자체 점검**: 아래 "점검 질문".
7. **추적성 검증**:
   ```bash
   python3 .claude/skills/requirements-analysis/scripts/trace_check.py --docs docs --stage swe3
   ```
   모든 CMP/IF가 MOD/MIF/FN에 연결되고(T3), 모든 MOD/MIF/FN이 CMP/IF를 가져야(T4) 한다.
8. **리뷰**: `aspice-stage-review` 스킬로 `stage-reviewer` 서브에이전트에 리뷰를 맡긴다. 통과 전에는 구현으로 넘어가지 않는다.

## 점검 질문

- 모듈 책임을 "그리고" 없이 한 문장으로 썼는가? 함수 이름이 한 가지 일을 말하는가?
- M1~M4에 해당하는 모듈이 모두 인터페이스를 가지는가?
- 함수마다 반환값(상태 코드)과 모든 오류 경로가 정의되어 있는가?
- 판단 로직이 결정표로 표현되어 있고 결정당 조건이 6개 이하인가?
- 함수 설계만으로 코드 없이 단위 테스트의 예상값을 계산할 수 있는가?
- 설계상 순환 복잡도가 10 이하인가? 매개변수가 4개 이상인 함수가 있는가?

## 보고
