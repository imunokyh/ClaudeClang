# 통합 테스트 (SWE.5)

개별 컴포넌트는 맞게 만들었어도 **연결했을 때 어긋나는 결함**(단위·범위 불일치, 호출 순서, 주기, 상태 공유, 오류 전파)을 찾는 것이 목표다. 그래서 통합 테스트는 **인터페이스를 중심으로** 컴포넌트 간 연동이 잘 되는지 확인하는 테스트 위주로 쓴다.

## 규칙

1. **인터페이스 중심**: 테스트는 컴포넌트 인터페이스(`*_if.h`, 아키텍처의 IF-nnn)를 기준으로 한다. 컴포넌트 내부 함수를 직접 부르지 않고, 공개 인터페이스와 최상위 진입점(주기 함수, 이벤트 진입점)으로만 구동한다.
2. **정해진 커버리지를 100% 달성할 때까지 반복해서 테스트 케이스를 추가한다.** 목표 지표는 CLAUDE.md "테스트 요건"이 정한다(현재: 통합 = 함수 커버리지 100% + 테스트 성공률 100%). 미달인데 완료로 보고하지 않는다.
3. **Stub/Mock은 필요할 때만, 과하게 의존하지 않는다.** 스텁은 **HW·OS 경계**(아키텍처가 식별한 지점)에만 둔다. 컴포넌트끼리는 실제 코드를 연결한다. 컴포넌트 사이에 mock을 끼우면 통합 테스트가 아니다.
4. **커버리지 달성만을 위한 의미 없는 테스트를 추가하지 않는다.**
5. **모든 테스트 함수에 Doxygen 주석**으로 목적, 입력값, 절차, 예상 출력값을 쓴다.
6. **경계값 분석, 동치 클래스, PICT 조합**을 활용한다.

공통 도구와 기준은 `unit-test-mcdc` 스킬과 같다. 그 스킬의 "테스트 함수 주석", "의미 있는 테스트", "테스트 설계 기법", "Stub/Mock 사용 기준"을 그대로 따르고, 이 문서는 통합 테스트에서 달라지는 점만 정한다. 도구 경로: `.claude/skills/unit-test-mcdc/scripts/`.

## 단위 테스트와 다른 점

| | 단위(SWE.4) | 통합(SWE.5) |
|---|---|---|
| 근거 | 상세 설계(함수·결정표) | 아키텍처(컴포넌트 인터페이스, 동적 동작) |
| 대상 | 함수 하나 | 컴포넌트 여러 개를 실제로 연결 |
| 스텁 | 다른 모듈 | **HW·OS 경계만** |
| 구동 | 함수 직접 호출 | 공개 인터페이스·최상위 진입점 |
| 커버리지 | MC/DC 100% | 함수 커버리지 100% |
| ID | `UT-nnn` ↔ `FN-nnn` | `IT-nnn` ↔ `IF-nnn` |

함수 커버리지는 llvm-cov의 함수 커버리지(`functions`)로 측정한다. 테스트 실행 중 한 번도 호출되지 않은 함수(static 함수 포함)가 있으면 미달이다. 통합 테스트는 공개 인터페이스로만 구동하므로, 호출되지 않는 함수는 연동 경로가 빠졌거나 죽은 코드라는 신호다.

## 인터페이스 중심 설계

`docs/swe2/`의 인터페이스(IF)마다 다음을 **빠짐없이** 케이스로 만든다. 이 단계의 테스트는 커버리지와 무관하게 필요하다.

| 관점 | 확인할 연동 결함 | 기법 |
|---|---|---|
| 데이터 전달 | 한쪽이 보낸 값을 다른 쪽이 같은 단위·범위로 해석하는가 (km/h ↔ m/s, 8비트 ↔ 16비트, 부호) | 동치 클래스(정상 대표값), 경계값(범위 끝±1) |
| 오류 전파 | 한쪽의 오류 상태 코드를 다른 쪽이 올바르게 처리하는가, 오류가 연쇄로 퍼지거나 삼켜지지 않는가 | 동치 클래스(무효 클래스), 결함 주입(스텁이 오류 반환) |
| 호출 순서·주기 | 호출 순서가 바뀌거나 주기가 어긋나도 안전한가, 초기화 전 호출은? | 상태 전이, 시간 경계(타이머 만료 직전·직후) |
| 상태 공유 | 두 컴포넌트가 같은 데이터를 볼 때 갱신 시점 차이로 불일치가 생기는가 | 순서 변형 |
| 다중 인터페이스 조합 | 여러 인터페이스 입력이 동시에 변할 때의 결과 | **PICT 조합**(입력 3개 이상) |
| 경계 신호 | 신호 무효·타임아웃·복귀 | 결함 주입 |

- 예상 출력값은 **아키텍처·요구사항**에서 정한다(실행 결과를 받아 적지 않는다). 컴포넌트 사이의 단위·범위·시점은 아키텍처의 인터페이스 표가 근거다.
- 케이스는 "어떤 연동 실수가 있으면 이 테스트가 실패하는가"를 목적 칸에 쓴다.

## 구조 규약

- 위치: `tests/integration/test_<시나리오 그룹>.cpp`, 실행 파일 `it_<그룹>`을 `tests/integration/CMakeLists.txt`에서 만든다. 단위 테스트와 같은 제품 코드 라이브러리를 링크한다.
- HW·OS 경계 스텁: `tests/integration/stubs/`. **입력 주입**(신호값, 무효, 타임아웃)과 **출력 관측**(명령 기록) 기능만 둔다. 로직을 넣지 않는다.
- 테스트 이름: `TEST(IT_<인터페이스>, <상황>_<기대>)`, 주석의 `@test IT-nnn`, `@trace IF-nnn`.
- 명세 `docs/swe5/integration-test-spec.md`: `IT-nnn | IF-nnn | 기법 | 사전 조건 | 입력·절차 | 예상 | 근거`(추적성 T7, T8).

```cpp
/**
 * @test IT-004
 * @brief signal 컴포넌트가 VehSpd 무효를 보고할 때 lock_ctrl이 잠금 명령을 바꾸지 않는지 확인한다.
 *        (노리는 연동 결함: 무효 상태 코드를 lock_ctrl이 무시하고 마지막 속도로 판단)
 * @trace IF-002
 * @par 입력값
 * 사전: VehSpd=20 km/h로 한 주기 실행하여 LOCK 출력. 입력: 스텁이 VehSpd 무효(STATUS_ERR_STATE) 주입
 * @par 절차
 * 1. 스텁으로 VehSpd=20을 주입하고 app_step()을 1회 호출한다. (LOCK 출력 확인)
 * 2. 스텁이 VehSpd 무효를 반환하게 하고 app_step()을 1회 호출한다.
 * 3. 스텁이 기록한 도어 잠금 출력을 읽는다.
 * @par 예상 출력값
 * 2번 주기의 잠금 출력은 변하지 않고(LOCK 유지), app_step() 반환은 STATUS_OK (SAF-001)
 */
TEST(IT_signal_lock, InvalidSpeed_KeepsLastCommand)
{
    /* ... */
}
```

## 반복 절차 (목표 커버리지 달성까지)

1. **명세 먼저**: 아키텍처의 인터페이스와 동적 동작에서 위 "인터페이스 중심 설계" 표로 케이스를 도출해 명세에 쓴다.
2. **테스트 작성**: 스텁(HW·OS 경계만)을 만들고 케이스를 구현한다.
3. **측정**: `docker compose run --rm dev tools/run.sh integration`
4. **실패 테스트가 있으면** 먼저 해결한다. 통합 테스트 실패는 대개 인터페이스 불일치다. 아키텍처와 비교해 어느 쪽이 틀렸는지 판단하고, 제품 코드 수정이 필요하면 **단위 테스트에 재현 테스트를 먼저** 추가한다(TDD).
5. **호출되지 않은 함수 찾기**: `build/reports/integration/html/index.html`의 함수 목록, 또는 `llvm-cov report <실행파일> -instr-profile=build/reports/integration/merged.profdata`의 함수 열(Missed Functions)에서 실행 횟수가 0인 함수.
6. **시나리오 설계**: 그 함수에 도달하려면 **공개 인터페이스에서 어떤 입력·순서·타이밍**이 필요한지 거꾸로 추적하고, 위 "인터페이스 중심 설계" 관점 중 어느 것에 해당하는지 정한다(대개 오류 전파, 상태 이력, 타이머 만료, 초기화 직후). 해당하는 관점이 없다면 그 함수가 필요한지부터 의심한다.
7. **테스트 추가 → 3번으로.** 100%가 될 때까지 반복한다.
8. **마무리 검사**: `tools/run.sh testdocs`, `tools/run.sh integration`, `trace_check.py --stage swe5`(모든 IF에 IT가 있고, 모든 IT에 IF가 있음).

## 막혔을 때

| 증상 | 판단 | 조치 |
|---|---|---|
| 공개 인터페이스로는 호출할 수 없는 함수 | 죽은 코드이거나 상위에서 이미 걸러진 값을 다시 검사하는 방어 코드 | 사용자에게 보고한다: 함수 이름, 호출 불가 근거, 선택지(코드 삭제 / 결함 주입으로 호출 / 안전 요구상 유지). 사용자가 정하기 전에는 통과라고 하지 않는다 |
| 도달하려면 HW 결함이 필요함 | 정상 동작으로는 안 나오는 경로 | 경계 스텁에 결함 주입 기능을 추가해 도달시킨다. 정당한 통합 테스트다 |
| 컴포넌트 내부 함수를 직접 불러야만 도달 | 규칙 1 위반 | 호출하지 않는다. 인터페이스로 호출할 수 없다면 위 첫 행으로 간다 |

측정 제외는 금지한다. 꼭 필요하면 사용자 승인을 받고 결과서와 PR에 적는다.

## 보고

호출한 쪽에 최종 `tools/run.sh integration`과 `testdocs`의 판정 줄(그대로 인용), 추가한 테스트 수, 인터페이스 커버리지, 사용한 스텁 목록, 호출 불가로 보고한 함수 목록(있다면)을 돌려준다.
