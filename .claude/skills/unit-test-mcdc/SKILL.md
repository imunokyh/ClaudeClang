# 단위 테스트 (SWE.4)

목표는 커버리지 숫자가 아니라 **상세 설계대로 동작하지 않는 결함을 찾는 것**이다. 커버리지는 "충분히 찔러 봤는가"를 재는 자일 뿐이므로, 숫자를 채우려고 의미 없는 테스트를 쓰지 않는다.

## 규칙

1. **정해진 커버리지를 100% 달성할 때까지 반복해서 테스트 케이스를 추가한다.** 목표 지표는 CLAUDE.md "테스트 요건"이 정한다(현재: 단위 = MC/DC 100%). 중간에 멈추거나, 일부 미달인데 완료로 보고하지 않는다.
2. **Stub/Mock은 필요할 때만, 과하게 의존하지 않는다.** 아래 "Stub/Mock 사용 기준".
3. **커버리지 달성만을 위한 의미 없는 테스트를 추가하지 않는다.** 아래 "의미 있는 테스트".
4. **모든 테스트 함수에 Doxygen 주석**으로 테스트 목적, 입력값, 절차, 예상 출력값을 쓴다. `tools/run.sh testdocs`가 검사한다.
5. **경계값 분석, 동치 클래스, PICT 조합**을 적극 활용한다.
6. **MC/DC 목표가 있으면 LLVM 도구로 케이스를 추가한다.** 이 스킬의 `scripts/`에 도구가 있다.

## 스킬에 들어 있는 도구 (`scripts/`)

| 스크립트 | 역할 |
|---|---|
| `llvm_cov_run.sh <unit\|integration> <지표> [빌드경로]` | 테스트 실행 파일을 모두 돌리고 `llvm-profdata`/`llvm-cov`로 병합·보고서(html, summary.json, mcdc.txt) 생성, 기준 판정, MC/DC 미달 시 분석까지 한다. 보통 `tools/run.sh unit`이 호출한다 |
| `coverage_gate.py` | `summary.json`을 기준(기본 100%)과 비교한다. **측정되지 않은 소스 파일**도 실패로 처리한다(링크 안 된 파일이 100%로 보이는 것을 막는다) |
| `mcdc_gaps.py` | `llvm-cov show --show-mcdc` 결과에서 미충족 조건(Cn), 이미 실행된 벡터, 보강 후보 벡터를 뽑는다 |
| `pict_cases.py` | PICT 모델 → 조합 표(GoogleTest 파라미터 표). 예상값은 만들지 않는다 |
| `check_test_docs.py` | 테스트 Doxygen 주석·단언·명세 ID 일치를 검사한다 (통합 테스트도 같이 씀) |

모든 도구는 컨테이너에서 실행한다(`docker compose run --rm dev ...`). 개별 실행 예:

```bash
docker compose run --rm dev python3 .claude/skills/unit-test-mcdc/scripts/mcdc_gaps.py build/reports/unit/mcdc.txt
```

## 구조 규약

- 프레임워크: GoogleTest (C++17). 제품 코드는 C이므로 헤더를 `extern "C" { ... }`로 감싸 포함한다.
- 위치: `tests/unit/<모듈>/test_<모듈>.cpp`, 모듈마다 실행 파일 하나(`unit_<모듈>`)를 `tests/unit/CMakeLists.txt`에서 만든다. **TDD로 구현하며 만든 테스트(`tests/tdd/`)와 섞지 않는다.** TDD 테스트를 옮기거나 복사하지 않고, 단위 테스트는 상세 설계(결정표·함수 설계)에서 새로 도출한다. 단위 테스트의 결과·MC/DC는 `tests/unit/` 실행 파일만으로 계산한다. 테스트는 인터페이스 헤더(`*_if.h`)로 호출한다. `static` 함수는 공개 함수를 통해 구동한다(`#include "x.c"` 금지).
- 스텁: `tests/unit/stubs/`. 제품 코드에 `#ifdef UNIT_TEST` 같은 테스트용 분기를 넣지 않는다.
- ID: 테스트마다 `UT-nnn`. 명세 `docs/swe4/unit-test-spec.md`의 표 첫 열이 ID이고, 같은 행에 대상 함수 `FN-nnn`을 쓴다(추적성 T5, T6).

## 테스트 함수 주석 (필수)

모든 `TEST`, `TEST_F`, `TEST_P` 바로 위에 아래 블록을 둔다. 태그가 하나라도 없거나 내용이 비면 `testdocs`가 실패한다.

```cpp
/**
 * @test UT-012
 * @brief 임계값(15 km/h)에서 잠금 명령이 나오는지 확인한다.
 *        (노리는 결함: >= 를 > 로 구현)
 * @trace FN-001
 * @par 입력값
 * speed_kph=15, door_closed=true, manual_override=false
 * @par 절차
 * 1. lock_decision_evaluate()를 위 입력으로 호출한다.
 * 2. 반환값과 출력 매개변수 cmd를 확인한다.
 * @par 예상 출력값
 * 반환 STATUS_OK, cmd == LOCK_CMD_LOCK (결정표 R1)
 */
TEST(lock_decision_evaluate, LocksAtThreshold)
{
    lock_cmd_t cmd = LOCK_CMD_NONE;

    EXPECT_EQ(STATUS_OK, lock_decision_evaluate(15U, true, false, &cmd));
    EXPECT_EQ(LOCK_CMD_LOCK, cmd);
}
```

- 이름: `TEST(<함수>, <상황>_<기대>)`. 한 테스트는 한 가지 동작만 본다(이름에 "And"가 들어가면 쪼갠다).
- **목적 칸에는 노리는 결함**을 쓴다("어떤 구현 실수가 있으면 이 테스트가 실패하는가"). 쓸 수 없으면 의미 없는 테스트다.
- 예상 출력값에는 **근거**(결정표 규칙 번호, 요구사항 ID)를 적는다.

## 의미 있는 테스트

커버리지 도구는 "실행했는가"만 본다. 다음은 숫자를 올려도 쓰지 않는다.

| 금지 | 이유 |
|---|---|
| 단언이 없는 테스트, 항상 참인 단언(`EXPECT_TRUE(true)`) | 결함이 있어도 통과한다 (`testdocs` TD3이 단언 없는 테스트를 잡는다) |
| 예상값을 코드를 실행해 나온 값으로 받아 적기 | 구현의 버그가 예상값이 된다. 예상값은 **상세 설계(결정표·함수 설계)**에서 계산한다 |
| 구현 세부(호출 횟수, 내부 순서)만 검증하는 테스트 | 리팩터링에 깨지고 동작은 검증하지 않는다 |
| 같은 결함만 노리는 중복 테스트 | 유지 비용만 늘린다 |
| 테스트 안에 제품 로직을 다시 구현해 비교 | 같은 실수를 두 번 한다 |

**변이 확인(필수)**: MC/DC를 채우려고 추가한 테스트는 이미 있는 코드에 대해 처음부터 통과하므로, 그 테스트가 실제로 조건을 검증하는지 확인한다. 해당 조건을 잠시 바꿔(`>=`→`>`, `&&`→`||`, 조건 제거 중 하나) 새 테스트가 **실패하는지** 본 뒤 즉시 되돌리고(`git diff src/`로 원복 확인), 결과를 결과서에 적는다. 실패하지 않으면 단언을 고친다.

## 테스트 설계 기법

함수마다 아래를 순서대로 적용해 케이스를 도출한다. 상세 규칙은 `system-test-case-generator/references/techniques.md`와 같다.

1. **동치 클래스**: 입력마다 유효·무효 클래스를 나누고 클래스당 대표값 하나. 무효 클래스는 케이스 하나에 하나만 넣는다(NULL, 범위 밖, 열거형 범위 밖).
2. **경계값 분석**: 임계값·범위 끝마다 분해능 단위로 경계 −1, 경계, 경계 +1. (`speed_kph`: 14, 15, 16 / 249, 250, 251)
3. **결정표 기반**: 상세 설계의 결정표 규칙마다 케이스 하나(규칙 번호를 예상값 근거로 적는다).
4. **PICT 조합**: 독립 입력이 3개 이상이고 조합 상호작용이 있을 때. 값은 2번·3번의 대표값·경계값에서 가져오고, 불가능한 조합은 제약으로 뺀다.
   ```bash
   docker compose run --rm dev python3 .claude/skills/unit-test-mcdc/scripts/pict_cases.py tests/unit/lock/lock.pict.txt --id PICT-LOCK-01
   ```
   출력 행을 `TEST_P` + `INSTANTIATE_TEST_SUITE_P` 파라미터 표로 붙이고, 행마다 **결정표로 예상값을 직접** 정한다. 모델 파일(`*.pict.txt`)은 저장소에 커밋한다(증적). 조합을 손으로 만들어 PICT 결과인 척하지 않는다.
5. **MC/DC 보강**(아래 절차): 위 기법으로 만든 케이스를 먼저 돌려 본 뒤 남은 미충족 조건만 추가한다. 기법 없이 커버리지 표만 보고 케이스를 만들지 않는다.

## Stub/Mock 사용 기준

- **기본은 실제 코드**를 쓴다. 대상 모듈이 부르는 같은 컴포넌트의 순수 함수는 스텁으로 바꾸지 않는다.
- 스텁이 필요한 경우: HW·OS 접근, 시간, 다른 컴포넌트의 인터페이스(`*_if.h`), 오류를 일으키기 어려운 의존성(결함 주입).
- 스텁은 인터페이스 헤더의 시그니처 그대로 만들고, 동작은 단순하게(고정 반환, 호출 기록) 유지한다.
- 한 테스트에 스텁이 3개를 넘거나 mock 호출 검증이 단언의 대부분이면 의존을 줄이도록 **설계**를 고친다(`test-driven-development` 스킬의 "Must mock everything → code too coupled").
- mock의 호출 횟수를 검증하는 것이 곧 테스트의 목적이 되면 안 된다. 관측 가능한 출력(반환값, 출력 매개변수, 외부로 나간 값)을 단언한다.

## 반복 절차 (목표 커버리지 달성까지)

1. **설계 확인**: `docs/swe3/`의 FN, 결정표, 오류 코드를 읽는다. 설계가 모호해 예상값을 정할 수 없으면 설계서부터 보완한다(코드를 보고 정하지 않는다).
2. **기법 적용**: 함수별 케이스를 위 "테스트 설계 기법" 1~4로 도출하고 `docs/swe4/unit-test-spec.md`에 `UT-nnn | FN-nnn | 입력 | 예상 | 근거` 행으로 쓴다.
3. **테스트 작성**: `test-driven-development` 스킬의 red-green-refactor를 따른다(구현 중이라면 실패부터 확인).
4. **측정**: `docker compose run --rm dev tools/run.sh unit`
5. **실패 테스트가 있으면** 커버리지를 보기 전에 먼저 해결한다. 코드가 설계와 다르면 코드를, 테스트가 설계와 다르면 테스트를 고친다. 어느 쪽인지 설계서로 판단한다.
6. **누락 파일이 있으면**: 테스트 실행 파일이 없거나 링크되지 않은 것이다. 테스트를 만든다.
7. **MC/DC 미충족이면** 출력 끝의 `MC/DC 미충족 조건 분석`을 읽는다(`mcdc_gaps.py`). 결정마다 미충족 조건 Cn, 이미 실행된 벡터, 보강 후보가 나온다.
   - Cn의 독립 영향을 보이려면 **Cn만 다르고 나머지(평가된) 조건은 같으며 결과가 다른** 벡터 쌍이 필요하다. 후보 벡터는 힌트다.
   - 후보의 **결과는 상세 설계 결정표**로 확인해 예상값을 정한다.
   - `- `(평가 안 됨)만 있어 Cn에 도달하지 못한 경우는 앞쪽 조건을 만족시켜 Cn에 도달하는 입력부터 만든다.
8. **테스트 추가 → 변이 확인 → 4번으로.** 100%가 될 때까지 반복한다.
9. **마무리 검사**: `tools/run.sh testdocs`(주석·단언·명세 ID), `tools/run.sh unit`, `trace_check.py --stage swe4`.

예(`if ((a > 0 && b > 0) || c > 0)`, 실행 벡터 `{F,-,F}=F`, `{T,T,-}=T`): C2 쌍은 `{T,T,-}=T`와 `{T,F,F}=F`, C3 쌍은 `{F,-,F}=F`와 `{F,-,T}=T`다.

## 완료 조건

`docker compose run --rm dev tools/run.sh unit`이 아래를 출력하고 종료 코드 0이어야 한다.

- 테스트 실패 0건
- `MC/DC 커버리지: N/N = 100.00%`, `판정: 통과`
- `누락` 줄 없음

## 막혔을 때

| 증상 | 원인 | 조치 |
|---|---|---|
| 어떤 입력으로도 Cn 쌍을 만들 수 없음 | 조건 결합(coupled)·함축 | 결정이 중복된 것이다. 상세 설계를 고치고 코드를 단순화한다(TDD 리팩터링). 측정에서 빼지 않는다 |
| 방어 코드 분기에 도달할 수 없음 | 상위에서 이미 걸러진 값 | 단위 테스트는 함수를 직접 부르므로 대개 도달 가능하다. 불가능하면 그 방어 코드가 정말 필요한지 설계에서 판단한다 |
| 한 결정의 조건이 많아 벡터 수가 폭증함 | 조건 N개 → 최소 N+1개 벡터 | 결정을 나눈다(중간 `bool` 변수 또는 판정 함수). 상세 설계부터 고친다 |
| `static` 함수를 직접 부를 수 없음 | 내부 함수 | 공개 함수를 통해 구동한다. 안 되면 모듈 분할을 설계에 반영한다 |

측정 제외(`LCOV_EXCL`, 파일 필터 변경, `-ignore-filename-regex` 확대)는 금지한다. 꼭 필요하면 사유를 정리해 사용자 승인을 받고 결과서와 PR에 적는다.
