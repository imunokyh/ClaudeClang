# 요구사항 분석 (SWE.1)

입력(고객·OEM·시스템 요구사항)을 **검증 가능한 SW 요구사항**으로 분해해 `docs/swe1/`에 쓴다. 이 산출물은 아키텍처·상세 설계·구현·모든 테스트의 기준이므로, 모호함과 누락은 뒤 단계 전체로 번진다.

## 분류 체계

```
요구사항
├── 기능 요구사항 (REQ-F-nnn 또는 분류=기능)      → docs/swe1/software-requirements.md
│   (OEM이 SWR-nnn 번호를 정해 준 프로젝트는 SWR-nnn 하나를 쓰고 `분류` 열로 기능/품질/제한/제약을 구분한다. 아래 REQ-F/Q/L/C는 SWR의 분류로 읽는다)
├── 기능 안전 요구사항 (SAF-nnn)   → docs/swe1/safety-requirements.md   ← 별도 문서
└── 비기능 요구사항                → docs/swe1/software-requirements.md
    ├── 품질 요구사항 (REQ-Q-nnn 또는 분류=품질)  — ISO 25010 특성으로 분류
    ├── 제한 (REQ-L-nnn 또는 분류=제한)         — 수치로 정해진 한계(자원, 시간, 크기)
    └── 제약사항 (REQ-C-nnn 또는 분류=제약)       — 설계·구현·개발 방식을 묶는 조건(언어, 표준, 도구, 인터페이스 형식)
```

| 종류 | 판별 질문 | 예 |
|---|---|---|
| 기능 | "시스템이 **무엇을 하는가**"(입력→동작→출력) | 차속이 15 km/h 이상이면 도어를 잠근다 |
| 기능 안전 | "고장·오용이 **위해(harm)**로 이어지지 않게 하는 요구인가" (HARA/안전 목표에서 도출) | 차속 신호 무효 시 500 ms 이내 안전 상태로 전환한다 |
| 품질 | "얼마나 **잘** 하는가"(측정 가능한 품질 속성) | 응답 시간 최대 100 ms |
| 제한 | "**넘으면 안 되는 수치**" | ROM 64 KB 이하, 스택 2 KB 이하 |
| 제약 | "**어떻게** 만들어야 하는가" | C11, 동적 메모리 금지, CAN 신호는 DBC 정의 따름 |

기능 안전 요구사항은 **본문 명세에 섞지 않는다.** `safety-requirements.md`에 따로 쓰고, 각 SAF에 ASIL, 안전 목표(출처), 안전 상태, FTTI(고장 허용 시간)를 적는다. 본문 명세에서는 SAF를 ID로 참조만 한다. ISO 25010의 "Safety" 특성 요구도 여기로 보낸다.

### 품질 요구사항 — ISO 25010

품질 요구사항은 ISO/IEC 25010 제품 품질 모델의 특성·부특성으로 분류한다. 적용한 **판(2011/2023)을 문서 머리에 적는다.** 판에 따라 이름이 다르다(2023판: Interaction capability = 2011판 Usability, Flexibility = Portability, Safety 추가). 전체 표와 측정 방법은 `references/iso25010.md`.

- 모든 품질 요구사항은 **특성 → 부특성 → 측정 기준(수치·방법·조건)**을 가진다. "빨라야 한다"가 아니라 "주기 10 ms 작업의 WCET 3 ms 이하(측정: 대상 HW, 최악 입력)".
- 적용하지 않는 특성은 삭제하지 말고 "해당 없음 — 사유"로 남긴다. 심사에서 "검토했는가"를 묻기 때문이다.

## 절차

1. **입력 확인**: 원 요구사항 문서와 버전. 없으면 요청한다. 추측으로 요구사항을 만들지 않는다.
2. **분해**: 원 요구사항 한 항목을 읽을 때마다 위 판별 질문으로 종류를 정한다. 한 문장에 종류가 섞이면 쪼갠다("0.5초 이내에 잠근다" = 기능 동작 + 품질 응답 시간).
3. **작성**: `references/templates.md`의 양식으로 쓴다. 요구사항마다:
   - 고유 ID (삭제해도 번호를 재사용하지 않는다)
   - 원 요구사항 출처 ID (상위 추적)
   - **한 문장 한 요구**: "shall"에 해당하는 동사 하나, 조건·동작·기대값이 한 문장
   - 입력·출력의 **단위, 범위, 분해능, 타이밍**
   - **검증 기준**(합격 조건): 어떤 입력에서 무엇이 관측되면 합격인가
   - 이상 입력(범위 밖, 신호 무효, 타임아웃) 동작 — 없으면 "정의 필요"로 질의 사항에 올린다
4. **질의 사항 관리**: 모호하거나(적절히, 빠르게, 가능하면), 모순되거나, 기대값이 없는 요구사항은 지어내지 말고 `질의 사항` 표에 남기고 사용자에게 묻는다. 합리적 가정으로 진행할 때는 `가정`으로 표시한다.
5. **검증 가능성 점검**: 요구사항마다 "이 요구를 어긴 구현을 시험으로 잡아낼 수 있는가"를 자문한다. 못 잡으면 다시 쓴다.
6. **추적성 검증**: 스크립트를 실행한다(아래).
7. **리뷰**: `aspice-stage-review` 스킬로 `stage-reviewer` 서브에이전트에 리뷰를 맡긴다. 통과 전에는 SWE.2로 넘어가지 않는다.

## 양방향 추적성

모든 요구사항(REQ-* 또는 SWR-*, 그리고 SAF-*)은 **이후 산출물과 양방향으로** 연결되어야 한다.

| 방향 | 의미 | 연결되는 산출물 |
|---|---|---|
| 상위 ← | 원 요구사항 → SW 요구사항 | 요구사항 표의 `출처` 열 |
| 하위 → | 요구사항 → 아키텍처(CMP/IF) → 상세 설계(MOD/FN) → 단위·통합 테스트(UT/IT), 그리고 요구사항 → SW 검증 테스트 | 각 산출물 표의 `상위 ID` 열 |

연결은 **표의 한 행**에 ID를 함께 쓰는 것으로 표현한다(첫 열 = 그 행이 정의하는 ID, 같은 행의 다른 ID = 연결). 형식과 검사 규칙은 `references/traceability.md`.

```bash
python3 .claude/skills/requirements-analysis/scripts/trace_check.py --docs docs --stage swe1
```

- SWE.1 단계에서는 `--stage swe1`로 출처 열과 안전 요구사항 문서 분리를 검사한다.
- 하위 산출물이 생긴 뒤에는 `--stage all`(생략 시 기본)로 전 구간을 검사한다. 요구사항이 개정되어 ID가 사라지거나 추가되면 아래 단계 산출물의 연결이 끊기므로 **개정마다 전 구간 검사를 다시 한다.** 개정 이력(변경 ID, 사유, 영향받은 산출물)을 명세 끝에 남긴다.
- 오류가 있으면 스크립트 출력(위치와 ID)대로 고친다. 검사를 통과시키려고 연결을 지어내지 않는다.

## 하지 않는 것

- 설계 결정을 요구사항에 쓰지 않는다("컨트롤러 모듈에서 처리한다" 같은 문장은 SWE.2의 몫이다). 단, 제약(REQ-C 또는 `분류`=제약)은 설계를 묶는 조건이므로 예외다.
- 검증할 수 없는 요구사항을 합격 기준 없이 두지 않는다.
